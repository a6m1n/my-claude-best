grill-me-v2

Pins down the requirements for a feature, change or idea before anything is planned or built. One question per message, each with options and a recommendation; every fact is looked up instead of asked; it ends with a Decisions Summary you confirm.

The problem it solves

You ask Claude for "a CSV export on the reports page". It starts building at once and guesses the columns, the filters and what happens with 200,000 rows. Or it asks first, but sends ten questions in one message, half of them about things the code already shows. The skill is built against five ways such a requirements talk can go wrong.

Without the skillGuesses become the spec. Open decisions are filled in silently, and nobody sees which ones were guessed.
grill-me-v2Every open decision goes to you, even one with a safe default. Nothing is planned or built before you confirm the summary.
Without the skillA wall of questions. Ten at once: you answer some, skip others, and the order is lost.
grill-me-v2One question per message, in the order the decisions depend on each other. The tree is updated after every answer.
Without the skillQuestions the code could answer. "Which database do you use?"
grill-me-v2Anything the code, docs or web can settle is looked up and noted with file:line or a link, never asked.
Without the skillA question with no recommendation. "A or B?" leaves the analysis to you.
grill-me-v2Each question has two or more options that are really different, with pros and cons for this project, and a recommendation with its reason.
Without the skillSilent agreement. Your first idea is taken as it is, even when the code shows a problem with it.
grill-me-v2It pushes back with evidence. After one or two rounds you decide, and your override is recorded with your reason.

When to use it, and when not

Use it for

  • A feature, change or idea that is still vague, where a wrong guess would be expensive.
  • Collecting or sharpening the requirements before any plan or code exists.
  • Stress-testing an idea: every open decision named, with options and their costs.

Not for

  • A plan, ticket or doc that already exists and has open points.Go through its points one at a time with settle; it uses the same question format for a review.
  • A written diff to review.A code review. This skill asks what to build, not about code already written.
  • Getting the change built, not only specified.A build loop from decision to commit. Its first step runs this same interview, but skips decisions with a safe default.
  • A large task where the route itself is still open.Think the route through first with meta-thinking, then interview on the chosen route.
  • A clear task with nothing left to decide.Go straight to planning or building; the interview would have nothing to ask.

How a run goes

You run /grill-me-v2 CSV export for the reports page. The diagram follows the skill's own order: read what is already there first, build a tree of open decisions, walk it one question at a time, then confirm. Each box is coloured by who does the step, and each arrow has a number: the list under the diagram says what happens on it.

You Main session (your conversation) End of the run (thick green border) Orange arrow: back into the loop

Start and read what is there

  1. 1You start the run with a topic: a feature, a change or an idea. You can add a file or a ticket for the skill to start from.
  2. 2The topic is really missing, both from your words and from the chat so far: the skill asks you once what to gather requirements for.
  3. 3With the topic named, the skill goes on to read what is already there.
  4. 4The topic is clear: the skill starts reading what is already there straight away.
  5. 5Before the first question, the skill takes a quick pass over what is already there: the project's code, its instruction files and rules, its architecture docs (it keeps in mind any note that says a doc is out of date), a ticket you linked. This makes the questions and the options concrete, with file:line where the code matters. A fact settled here never becomes a question. What is still open becomes a decision tree. Decisions depend on each other: whether the export runs in the browser or on the server decides whether file size is a question at all. The skill keeps the open decisions as a queue in that order and shows the count, such as "0 of 6".
  6. 6It takes the next open point in the tree and first asks itself: is this a fact or a decision?

One branch at a time

  1. 7A fact is anything the environment can settle: the files, the code, the docs, the web. Example: "Which CSV library does the project already use?" The skill looks it up and never asks you.
  2. 8The fact is noted with its file:line or link and shapes the questions that follow; it is not counted as one of your answers.
  3. 9A decision is yours: product judgment, scope, taste, priority, how much risk you accept. The skill puts every one to you, even one it could settle with a default, because you asked to be questioned. (When the same interview runs as the first step of a build loop (a skill that takes one change from decision to commit), the loop skips the decisions that have a safe default.)
  4. 10One point per message, never a list. The point has a title with "Point N of M", a problem you can follow with no earlier context, two or more options that are really different, each with pros and cons for this project, and a recommendation with its reason. When only one answer makes sense, the skill says so and asks you to confirm it. When "take a default now and come back later" is a real option, it is listed with what would reopen it. When the skill has no evidence for a recommendation, it says what it would need instead of forcing a pick. Then it stops and waits.
  5. 11Your answer goes to one check: what kind of answer is it?

Your answer

  1. 12You disagree. The skill acts as an independent consultant, not as someone who agrees with everything. It answers with specific evidence and does not give in at the first push back. When you show something it missed, it says so and changes its recommendation.
  2. 13If you still disagree after one or two rounds of real argument, it states both positions and you decide. The record says so: "You chose X over my recommendation Y, because …".
  3. 14Your answer is unclear, or you say "you decide".
  4. 15Unclear: the skill asks one focused follow-up question. If that does not settle it, the recommendation becomes the decision and is recorded as a default. "You decide": the recommendation becomes the decision, and the notes say you handed it over. Either way the Decisions Summary shows the decision was not your own pick.
  5. 16You pick an option, or you say "skip". A skip is recorded, and the run moves on.

Next branch

  1. 17The skill confirms the answer in one sentence: whether you followed or overrode its recommendation, or whether it revised the recommendation after your argument, with the count. Example: "Resolved: Option B, over my recommendation A (3 of 5)." Then it updates the tree: an answer can open new branches, make others unneeded, or change the order, and the skill announces the new total. A new concern you raise along the way joins the queue too; the current point is finished first.
  2. 18Decisions are still open: the next point comes at once, in the next message.
  3. 19Every queued question is answered: the skill writes the result.

Confirm and hand over

  1. 20The Decisions Summary is a table with one row per question: number, question, decision, notes. The notes hold what came out of a debate, your overrides, defaults taken on an unclear answer, and decisions you handed over. Under it comes one paragraph: "My read: we want [what] so that [end state], under [the decided constraints]." The skill asks you to confirm this shared understanding.
  2. 21You do not confirm: nothing is planned or built yet. The interview runs until you and the skill understand the task the same way, not until the questions run out, so what is off goes back into the tree as new decisions.
  3. 22You confirm. Where the run goes now depends on how it was started.
  4. 23Started on its own: the skill offers the next steps and starts none of them itself. You pick one: a planning step that drafts a plan; the build loop (the loop that takes one change from decision to commit), with these answers passed in as decisions already made, so its own questions have nothing left to ask; a ticket; or a requirements file, saved in a dated folder where the project keeps its working notes, or in a temporary folder when it has none.
  5. 24Started as the requirements step inside a build loop: the loop waits for your yes, and then goes on to its next stage. No next steps are offered.

What a question looks like

Every question comes in one message, in the same parts. Then the skill stops and waits for your answer.

PartWhat it holds
Point N of MWhere you are in the queue; M changes when an answer opens or closes branches
ProblemWhat is still open, why it matters, and how the options differ, readable with no earlier context; file:line where the code is part of it
OptionsTwo or more that are really different, each with what it means, pros and cons for this project. One sensible answer: the skill says so and asks you to confirm
My recommendationThe option it would pick and why, based on this project's code and docs. No evidence: it says what it would need
Point 2 of 6: Where the export runs

Problem: the reports page can show up to 200,000 rows, but it loads them from the server 500 at a time (reports/api.py:88). Where the CSV is built decides whether file size and timeouts are questions at all.

Option A: in the browser. Build the file from the rows the page already has. Pros: no new endpoint; done in a day. Cons: it exports only the 500 loaded rows; a large export can freeze the tab.

Option B: on the server. A new endpoint writes the CSV and the browser downloads it. Pros: any size; the same filters as the page. Cons: one more endpoint to secure and test.

My recommendation: Option B, because the page already gets its data from the server in pages, so a browser export would quietly miss most rows.

What you are asked

The skill stops for you in four cases.

Each open decision

Scope, product judgment, taste, priority, how much risk you accept. One per message, in the format above. You can pick, push back, skip, or say "you decide".

The topic, once

Only when neither your words nor the chat say what to gather requirements for.

When you disagree

It answers with evidence. After one or two rounds of real argument it states both positions and you decide.

You want Option A to ship this week; I still recommend B because A drops rows. Your call: A or B?
The confirmation

You see the Decisions Summary and its "My read" paragraph, and confirm the shared understanding or say what is off. Run on its own, the skill then asks which next step you want and starts none by itself.

What makes it different

One question per message

Several at once confuse you and lose the order in which decisions depend on each other.

Questions follow the decision tree

An early answer changes which questions come next, so the tree is updated after every answer.

Every question has a recommendation

A question without one is half the work pushed onto you.

Facts are looked up, never asked

Only decisions are yours. What the code, docs or web can settle is settled there.

Even safe defaults go to you

You asked to be questioned. A build loop that uses the same interview skips those defaults; this skill does not.

Only real options

Padding hides the real choice. With one sensible answer, the skill asks you to confirm it.

No forced recommendation

Without evidence it says what it would need, instead of guessing with confidence.

It pushes back with evidence

Silent agreement is the failure the skill is built against; your override is recorded with your reason.

Ends on your confirmation

The goal is a shared understanding, not an empty queue, so nothing is planned or built before you confirm it.

Offers the next step, never starts it

What comes next (a plan, a build, a ticket, a saved file) is your choice.
