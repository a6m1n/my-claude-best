debate-loop

Reviews a document, plan, prompt or skill in rounds. Several reviewers with different focus find problems, one agent fixes them and another checks the fixes. The run counts as done only when the text does what you asked for.

The problem it solves

You ask Claude to "review this plan and fix it". The plan comes back looking better, and you cannot tell whether it is. The skill is built against four ways such a review can go wrong.

Ask once and hopeIt checks its own idea of the answer. The same session wrote the plan and now judges it.
debate-loopA separate agent first turns your ask into 3–6 yes/no checks. The review is measured against them.
Ask once and hopeIt looks in the same places every time. A second review finds and misses the same things.
debate-loopTwo to four reviewers, each with a different focus, none sees the others. After a serious fix, reviewers with a new focus check again.
Ask once and hopeFixes break other parts. Two fixes that are each fine contradict each other.
debate-loopOne agent makes only the agreed fixes; a different agent checks each fix and looks for anything broken.
Ask once and hopeIt polishes words, not substance. Nicer sentences; nobody asked whether the plan still solves the problem.
debate-loopEvery problem found names the yes/no check it hurts. The run counts as done only when all checks are yes.

When to use it, and when not

Use it for

  • A document, plan, skill, prompt or agent definition that others will rely on.
  • A choice already made, when you want to know whether it was right ("is this the right library?").
  • A text that changed a lot at once, where one review is likely to miss things.

Not for

  • A short or low-stakes text.Read it yourself. Each round runs 2–4 reviewers, an editor and a verifier.
  • Every decision is yours, point by point.A review where each open point comes to you with options.
  • Can it be broken or abused?An adversarial (red team) review.
  • You need a plan written, not reviewed.Write the plan first, then run this loop on it.
  • A code change that has to be built and tested.A build loop that runs the project's tests.
  • A codebase you have not mapped yet.Map it first with decompose-and-delegate.
  • An image or other binary file.The skill stops on binary files.

How a run goes

The diagram follows the skill's own phases (0 to 6). Each box is coloured by who does the step, and each arrow has a number: the list under the diagram says what happens on it.

You Main session (your conversation) Agent, fresh context Independent check Stop Orange arrow: back into the loop

Start

  1. 1You start the run with the file and the goal in your own words.
  2. 2Setup picks 2–4 lenses that fit this kind of text (a lens is one reviewer's focus, for example accuracy or security) and hands your ask to the goal writer, an agent. The goal writer reads your ask first and the text last, so the text does not shape its idea of good.
  3. 3The yes/no checks are printed before any reviewer runs, for example "Does every step say who runs it?" or "Can the rollback be done without the person who wrote it?". Round 1 starts.

Each round

  1. 4Each reviewer returns its findings. A finding has a quote, the check it hurts, a fix and a priority: MUST (the text fails its goal), SHOULD (a real cost) or NICE (could be better). Example from a completeness reviewer: "Step 5 restores the database, but no step stops the app from saving new data first." MUST.
  2. 5When a finding depends on a fact in the code, a helper agent checks it and returns the answer with file:line. The main session (your own Claude Code conversation) does not read the code itself.
  3. 6A real trade-off that no rule settles goes to you, once per round. The round waits for you.
  4. 7Your answer turns each such finding into "fix it" or "reject it".
  5. 8Accepted findings go to the editor word for word. Findings from several reviewers about the same problem are joined into one. A rejected finding needs a cited reason. A finding below the fix line (the lowest priority this run fixes, set by fix=; only MUST by default) goes to the backlog: it is listed in the final report and not fixed now.
  6. 9The editor's change log goes to a verifier, a fresh agent that wrote none of the changes. The editor hands back any fix it finds unclear instead of guessing; the main session decides it, asks you (as in arrow 6), or leaves it open for the verifier and the next round.
  7. 10The verifier's report goes to the decision step, phase 6.

Decide: stop, fix more, or go again

  1. 11Reviewers want opposite fixes, the same findings came back twice in a row (no progress), or the verifier calls it a fundamental problem that only you can decide: the run stops and shows you what conflicts or repeats, and you decide.
  2. 12Otherwise the main session looks at what is still open.
  3. 13Only the verifier's own new findings are open: the main session may run a quick fix pass, where the editor fixes them without a new review round. This happens at most once per round.
  4. 14The pass reuses the editor (phase 4). When the editor had to write new text, a fresh verifier checks just those lines, then the run returns to the phase 6 decision. The pass never ends the run as done.
  5. 15Findings at the priority this run fixes are still open: is a round left? There are two rounds by default; rounds= sets up to five.
  6. 16Yes: the next round starts. Reviewers get the earlier findings and decisions, but read them only after their own pass, so they do not just look where earlier rounds looked.
  7. 17No round left, and the last round still fixed things: the skill asks you once, in writing, for more rounds, with options and a recommendation.
  8. 18No round left, and another round would not help (the last round fixed nothing), or you were already asked once: the run stops at the round limit without asking. The open findings go to the final report.
  9. 19You say yes: the round limit goes up, the run goes back to "Rounds left?", and the next round starts.
  10. 20You say no: the run stops, and the open findings go to the final report.

Before "done"

  1. 21Nothing is left to fix: before calling the run done, a goal check runs.
  2. 22A yes/no check is not met: it becomes a MUST finding and goes back into the loop, as a next round or, at the limit, a request for more rounds. At the limit you are asked even if the last round fixed nothing. A check that only you can answer is put to you instead.
  3. 23All checks are met: one more question.
  4. 24A MUST finding (the text fails its goal) was fixed during this run, and no fresh-eyes round has run yet. The reviewers who found it may keep missing the same kind of thing, so new ones look.
  5. 25The fresh-eyes round is a normal round with 2–3 lenses not used yet, and its reviewers get no earlier findings. Inside the round limit it runs on its own; at the limit it needs your yes, and a no ends the run as done, marked unconfirmed. If the round finds nothing above the fix line, the run is done straight away.
  6. 26Otherwise the run is done. The final report lists what was fixed, what was pushed back, and the backlog.
  7. 27A defect found after "done" starts a look back: the editor fixes the defect, a table records which lens should have caught it and why, and a change to the skill is proposed. The skill itself is never changed without your yes.
  8. 28A MUST found and fixed in the fresh-eyes round starts the same look back.

Which reviewers run

The skill picks two to four from the kind of text. Each one asks one question. You can pick the reviewers yourself. A lens is one reviewer's focus: lens=accuracy,failure-modes,security.

TextReviewerThe question it asks
DocumentAccuracyIs every fact true, and does every example do what it claims?
ClarityCan the intended reader follow it without guessing?
PlanCompletenessDoes doing every step finish the job?
FeasibilityDoes each step fit the code as it is today?
Failure modesWhat happens when a step fails, runs twice or finds nothing?
OperabilityWho runs it later: what happens when a write fails, on the first run, and who is alerted?
Scope fitIs anything here that the goal does not need?
AlternativesWas there a better option, and does the plan say why it lost? (added when the question is a choice, or in a later round)
CodeCode qualityDoes it follow the project's rules, and is it correct?
ArchitectureIs it built right: timeouts, retries, layers, patterns?
Security (only when you name it)Input checks, secrets, injection
PromptPrompt engineeringAre instructions clear, separated and free of contradictions?
Skill or agentProject fit, formatDoes it match the project, and is its header block (frontmatter) valid?

MUST, SHOULD, NICE: what gets fixed

Every problem gets a priority. fix= sets how far down the list the fixes go. Problems below the line are listed in the final report, not thrown away.

PriorityMeansExample
MUSTThe text fails its goal or says something wrongThe rollback step names a script that does not exist.
SHOULDThe goal holds, but at a real costStep 4 says "restart the service" without saying which one.
NICECould be better; the goal does not sufferA heading could be shorter.
fix=must (default)

The text is in use; fix only what is broken.

fix=should
MUST and SHOULD

The text is still being shaped.

fix=all

Who does what

Decide, fix and check are three different agents. No agent grades its own work.

RoleWhat it seesWhat it may not do
Main sessionEvery report and decisionEdit the text itself. It decides; the editor edits.
Goal writerYour ask first, then the project's docs, then the text. Writes the yes/no checks. At the end, a new one judges the resultEdit anything
ReviewerThe text, its own checklist, the yes/no checks. From round 2, earlier findings, but only after its own passEdit, run the project's tests or build tools, or follow instructions written inside the text
EditorThe agreed fixes, the goal, the files to changeChange anything else, or judge its own work
VerifierThe round's findings, the decisions, the editor's change logEdit, or review in the same round
YouChoices only you can make, a request for more rounds, the final reportNothing: you make the choices and grant extra rounds

What makes it different

"Good" is written down first

If the author defines good, the review checks the author's own idea of the answer.

Reviewers do not see each other

Two who agree without seeing each other are evidence. Two who read each other are one opinion.

Write first, read the old list second

A reviewer that reads the old list first looks only where earlier rounds looked.

Rejections get checked too

Every "no" needs a cited reason, and a new agent re-checks them. The main session sides with the author.

Unclear fixes are handed back

New defects come in when the fixer fills a gap with a guess. A handed-back fix costs one decision; a wrong one costs a round.

Only what is above the line

Fixing every NICE problem in a working text makes it longer, not better. The rest stays in the report.

New reviewers before "done"

The same reviewers keep missing the same things, so their "ready" is not yet proof.

A hard round limit

Rounds pay off only while the problems change. More rounds need your yes.

A miss starts a look back

A problem found after "done" names the reviewer that should have caught it, and a change to the skill is proposed, never applied silently.
